## Technical Context

- **Architecture**: A state-machine driven simulation loop using `requestAnimationFrame`. The elevator's behavior is managed through a series of states to ensure the complex sequence of door animations and person movement is synchronized.
- **Patterns**: 
    - Factory pattern for creating person objects.
    - State machine for managing asynchronous-like sequential animations in a synchronous loop.
- **Libraries/Frameworks**: Three.js (v0.147.0), OrbitControls.
- **Key Implementation Details**:
    - **Transparency**: `renderer.sortObjects = true` and `depthWrite: false` are used on transparent materials to prevent z-fighting and visibility issues.
    - **Reparenting**: Uses `THREE.Object3D.attach()` when a person enters or exits the elevator to preserve their world position, preventing teleportation bugs.
    - **Coordinate System**: Y is vertical; Z+ is in front of the elevator doors.

## Strategy & Approach

- **Approach**: A "YOLO" approach was taken to implement the full logic immediately without intermediate steps, following all hard requirements (H1-H8) strictly from the start.
- **Why this approach**: The simulation requires tight synchronization between the elevator's position, door states, and person movement. A state machine is the most reliable way to handle this in a single `requestAnimationFrame` loop without using ES6 modules or complex async/await structures that might conflict with the plain-script requirement.
- **Assumptions**: Assumed standard browser behavior for `DOMContentLoaded` and that the provided CDN links are accessible.
- **Risks Identified**: The primary risk is the complexity of the state machine transitions; any missed state could lead to a "stuck" simulation (e.g., doors never closing).
